## 审查发现

### [P2][F1] 设备协议业务动作横跨 API、应用层和数据库多个一致性边界

位置：[api/device_api.go:63](../../api/device_api.go#L63)、[api/device_api.go:323](../../api/device_api.go#L323)、[app/device.go:380](../../app/device.go#L380)、[app/credential.go:362](../../app/credential.go#L362)、[db/device.go:224](../../db/device.go#L224)、[db/device.go:249](../../db/device.go#L249)。

`deviceAuth` 负责认证且写入 `Touch`，随后 `handleHeartbeat` 独立写入 `RecordHeartbeat`，再读取发布、判断配置变化、调用凭据步骤并构造响应。同一心跳两次更新最近在线。心跳观察按槽位 public ID 落库，凭据步骤另行复核设备当前绑定，配置响应却取自之前认证产生的设备快照。

发生设备换绑或配置变更时，观察写入、凭据决策和响应快照缺少共同的业务一致性边界。凭据内部锁已解决签发流程的互斥问题，此处仍有设备协议整体上的状态分散。

建议 `api` 层专注解码、认证、错误映射及响应编码。认证返回经过验证的设备主体和请求字段。`app` 层提供完整的设备注册与心跳业务入口，复核当前绑定，取得确定快照，统一规划响应及协调凭据步骤。心跳观察合并为一次、关联当前绑定的条件写入。管理端变更与绑定决策遵循同一设备一致性约束，锁范围按真实任务收紧。

凭据签发保留意图行、按设备串行及补偿机制，SQLite 事务不跨外部 CLI 调用。无需新建通用事务或仓储框架。验收要求同一心跳的观察值与响应对应确定的设备绑定，配置、凭据、换绑及撤销之间的交接可在应用层独立测试。

### [P2][F2] 默认模板与发布槽位共用请求，但缺少共同的提交边界

位置：[app/settings.go:133](../../app/settings.go#L133)、[app/settings.go:146](../../app/settings.go#L146)、[app/settings.go:171](../../app/settings.go#L171)、[api/settings.go:106](../../api/settings.go#L106)、[frontend/ConfigView.vue:39](../../frontend/src/components/ConfigView.vue#L39)。

`PublishInput` 同时容纳客户端包、启动器与默认模板。前两项在 SQLite 事务中写入，模板先经独立文件操作提交。模板提交成功、槽位事务失败时，调用方收到失败，但模板已生效。这是代码注释明确承认的窗口，然而上级 `docs/contract/updates.md` 仍描述三个内容一起提交的语义。

前端已经分别编辑模板与发布槽位，模板读取也有独立路由。建议将模板写入归 `PUT /api/admin/template`，发布请求仅包含工件，保留双槽位 SQLite 原子提交。删除 `PublishInput.DefaultTOML` 及模板与发布之间的顺序协调。只有确有三项组合提交的业务需求时，才需要将模板迁入 SQLite 的共同事务。

验收要点：独立模板保存与发布各自有确定结果，两个槽位同时发布仍保持原子性。先修订上级 HTTP 契约及当前实现说明。

### [P2][F3] 附加命名 UNIQUE 索引没有按其对约束的影响处理

位置：[db/db.go:409](../../db/db.go#L409)、[db/db.go:416](../../db/db.go#L416)、[db/db.go:441](../../db/db.go#L441)。

当前参考库结构检查允许附加命名索引，目的是兼容只影响查询性能的运维索引。`splitIndexes` 按 SQLite 的 `origin` 分类，随后只遍历参考库的命名索引，检查隐式唯一约束的形状。附加的显式命名唯一索引也会被忽略，但这种索引改变数据库能够接受的数据集合，与检查的契约意图不一致。

建议只允许结构验证范围外的普通非唯一索引，附加显式唯一索引应报告结构差异。保留已接受的部分索引谓词文本比较取舍。

### [P3][F4] `release` 表的行含有两个独立槽位及多组空字段状态

位置：[db/db.go:49](../../db/db.go#L49)、[db/release.go:27](../../db/release.go#L27)、[db/release.go:106](../../db/release.go#L106)、[db/release.go:147](../../db/release.go#L147)、[api/device_api.go:295](../../api/device_api.go#L295)。

当前发布表按平台一行保存客户端包与启动器两组字段。槽位缺失表现为多列空字符串及默认值，写入须先建平台行再针对槽位更新。清除启动器需要置空多个字段，再检查是否删除平台行。启动器和客户端包本身都具有版本、地址、摘要及签名四个公共字段。

建议以每个真实发布槽位为一行，通过 `(platform, slot)` 约束唯一性，公共工件字段只声明一组。客户端包保留其说明与自动更新策略。删除槽位直接删除对应行，存在性由记录本身表达。一次同时发布两个槽位仍在同一 SQLite 事务进行。管理面按平台聚合属于读取及展示逻辑，现有 HTTP 形状可由查询结果构造。

此方案主要减少表示无效组合的空状态及重复 SQL，前端及设备策略效果保持原有语义。需先更新数据契约，并按当前明确迁移策略修改线上库。

### [P3][F5] 增量更新协议及部分辅助机制可进一步简化

位置：[api/device_api.go:42](../../api/device_api.go#L42)、[api/device_api.go:259](../../api/device_api.go#L259)、[api/device_api.go:381](../../api/device_api.go#L381)。

`appUpdateKnown` 和 `unchanged` 形成跨两端的缓存协商协议。服务端根据摘要选择完整或精简响应，客户端必须记住完整 offer，导致两条独立处理路径。按最多 200 台设备、30 秒心跳及假设 2 KiB 说明估算，同时更新期间重复说明约 13.3 KiB/s，尚有 URL、签名及编码开销。对目前实际约 8 台设备，重复说明约 0.53 KiB/s。

建议始终随心跳传递当前完整的可升级 offer，客户端按版本与摘要判重，更新策略及元数据直接采用当前值。配置正文仍只在配置摘要改变时下发。删除 `appUpdateKnown` 与 `unchanged`、相关字段约束、缓存解释及双形状测试。客户端本轮 F5 有对应建议。
